## 総合判定

| 項目 | 判定 |
|------|------|
| **実装開始可能判定** | **GO_WITH_REFACTOR** |

**理由（要約）:** 現行アーキテクチャ（State + Pending + 導出 EffectStack）は Wiki コアループと整合しており、全面リライトは不要。ただし **Tier 1 基盤修正（パワー計算・カードデータ・エラッタ）を完了するまで Tier 4 以降の本格実装は着手不可**。Event 層導入や Pending 分割は Tier 3 以降の段階的リファクタとして並行可能であり、実装開始そのものを阻害しない。

---

## 1. 現行設計で進めるべきか

### 結論: **はい — 骨格は現行設計のまま進める**

4 文書はいずれも、現行エンジンの **構造選択そのものを否定していない**。根拠は以下の通り。

| 観点 | 評価 | 根拠文書 |
|------|------|----------|
| フェイズ・勝敗・反応窓 | Wiki HIGH / 実装 HIGH | spec-review §確定仕様、state-gap §問題なし |
| Pending 10 種 + EffectStack 導出 | `timing.md` と 1:1 対応 | state-gap §問題なし、event-architecture §5.4 |
| 命令型 `applyAction` パイプライン | Legend 1–3 は Phase 0 で動作可能 | event-architecture §1.4、roadmap §方針 |
| 全面 Event Sourcing / 単一 Pending union | 却下（過剰・移行コスト大） | event-architecture §5.4 代替案比較 |

**採用継続すべき設計原則:**

1. **Pending が正** — ブロック状態・プレイヤー入力待ちの唯一のソース
2. **EffectStack は導出** — 優先順位の単一ソース。直接 mutate しない
3. **Action = プレイヤー意図** — UI / AI / ネットワーク同期の単位
4. **State = スナップショット** — ゾーン・修飾子・勝敗。解決ロジックは持たない

**現行設計で進めてはいけないこと:**

- Tier 1 未完了のまま個別カード効果（Tier 4）の大量実装
- Event 層の全面導入を Tier 2 検証より先に行うこと（roadmap「やってはいけない順序」）
- Pending / EffectStack の構造自体の作り直し

## 2. リファクタリング後に進めるべきか

### 結論: **部分的リファクタは Tier 1 と並行または直後。全面リファクタ待ちは不要**

「リファクタ」の意味を 3 段階に分けて整理する。

| 段階 | 内容 | 実装開始との関係 |
|------|------|-----------------|
| **R0: 必須修正（Tier 1）** | `countAvailablePower`、cards.json 突合、エラッタ統一 | **実装開始の前提条件**。これはバグ修正に近く、リファクタというより基盤整備 |
| **R1: 低リスク構造改善（P1）** | `pendingScry` 削除、`deferredBattleEntry` の Stack 登録、hold-ready 統合 | Tier 2 検証と並行可。完了を Tier 4 の必須条件にはしない |
| **R2: 中〜大規模改善（P2–P3）** | Event 層 Phase 1–2、`pendingEffectChoice` 分割、TurnModifiers 汎用化 | **Tier 3 以降**。新規カード追加の規約固定後に段階導入 |

**判断:**

- **R0 完了前:** コアループ検証・カード実装ともに信頼性が担保できない → 本格実装は待つ
- **R0 完了後:** 現行設計のまま Tier 2 検証 → Tier 3 スコープ ADR → Tier 4 へ進んでよい
- **R1/R2:** 実装を止める理由にはならない。カード増殖に伴う保守コストを抑えるため、roadmap の M1 以降で計画的に実施

event-architecture.md の結論「全面リライトではなくハイブリッド構成」と roadmap の「Event 層は Tier 3 以降」は一致しており、**リファクタ後に初めて着手** ではなく **限定リファクタを実装と並行** が正しい解釈である。

## 3. 最大の技術的リスク

### 単一最大リスク: **仕様確定済みルールのエンジン未実装 — 敵マルチ→パワー加算（I-01 / T1-04）**

| 項目 | 内容 |
|------|------|
| Wiki 確定度 | **HIGH**（atwiki 110, FAQ, core-rules） |
| 実装状態 | `canAffordPower` / `payPowerCost` が `player.power.length` のみ |
| 影響範囲 | ラッシュ可否、オペ使用、コスト判定 — **全デッキ・全フェイズに波及** |
| 深刻度 | 対戦結果が公式と異なる。**サイレントバグ**（クラッシュしない） |
| 4 文書の一致 | spec-review I-01、state-gap P0-1、event-architecture §9、roadmap T1-04 — 全員が最優先と明示 |

### 構造上の最大リスク（中長期）: **`pendingEffectChoice` の God Object 化 + 横断状態の散在**

| 項目 | 内容 |
|------|------|
| 現状 | 14+ kind、1500 行超の `pendingChoices.ts`、書き込み箇所ゼロの `simultaneousGroupId` |
| トリガー | Legend 4+ カード追加、選択 UI 系 effectId の増殖 |
| 影響 | 回帰テスト困難、hold-ready boolean クリア漏れ、Stack 外 Pending（`deferredBattleEntry`）による UI/AI 乖離 |
| 緩和 | Tier 3-12 分割、Tier 3-11 Event 層、R1 の Stack 統合 — いずれも Tier 2 安定後 |

### データ品質リスク（実装と同等に重大）: **cards.json ↔ Wiki 未突合（I-02 / T1-05）**

- verify-wiki-effects 未実行（1810 枚）
- RS-143 等 5 枚の効果文欠落、L3 UNKNOWN 約 40 枚
- エラッタ差分（C-06: RS-003/052/058/065 が errata.ts 外）

効果文が誤ったまま EffectHandler を実装すると **二重作業 + 誤動作の焼き付け** になる。roadmap は Tier 4 を Tier 1 より先にやることを明示的に禁止している。

### プロダクト判断リスク: **ウイング・チェイス・JC/RC の v1 スコープ未決定（I-05〜07）**

- ルールは Wiki HIGH だがエンジン未実装
- 依存カードが複数存在。スコープ外と決めずに Tier 4 に入ると手戻りが発生
- roadmap M2 で ADR 化を必須としている

## 5. 実装開始可能判定

### 判定: **GO_WITH_REFACTOR**

### 判定基準と該当理由

| 基準 | 状態 | 評価 |
|------|------|------|
| Wiki コアループ仕様の確定度 | フェイズ・ラッシュ・バトル・ダメージ = HIGH | ✅ 着手可能領域が明確 |
| 現行 State / Pending 設計の妥当性 | 80%+ 整合、構造否定なし | ✅ 現行設計継続 |
| 仕様確定済みの実装ギャップ | I-01 パワー計算 = **未実装** | ⚠️ Tier 1 完了まで本格実装不可 |
| カードデータ品質 | verify 未実行、UNKNOWN 40 枚 | ⚠️ Tier 1 / T4-DATA 必須 |
| アーキテクチャ移行方針 | Event 層は段階導入、全面リライト不要 | ✅ リファクタと実装の並行可 |
| プロダクトスコープ | ウイング・チェイス・JC/RC 未決 | ⚠️ M2 ADR 後に Tier 3–4 本格化 |
| 実装ロードマップ | Tier 依存・工数・DoD が定義済 | ✅ 実行可能な計画 |

### 各判定の意味

| 判定 | 条件 | 本プロジェクト |
|------|------|----------------|
| **GO** | 基盤完了、構造変更不要、即 Tier 4 可 | **該当しない** — T1-04 等の未完了あり |
| **GO_WITH_REFACTOR** | 骨格は妥当。限定の基盤修正・段階リファクタ後に本格実装 | **該当** — 下記アクション |
| **STOP** | 設計破綻、仕様未確定、全面作り直し必要 | **該当しない** — 4 文書とも構造継続を推奨 |

### GO_WITH_REFACTOR の具体的アクション

**今すぐ開始してよいこと:**

1. **Tier 1（M0）** — `countAvailablePower`、verify、エラッタ、5 枚修正（並行バッチ A/B/C）
2. **Tier 2 検証準備** — T1-04 マージ後のラッシュ・コスト回帰テスト設計
3. **ドキュメント修正** — T1-10（禁止カード・先攻記述）

**Tier 1 完了後に開始:**

4. **M1** — コアループ E2E、`deferredBattleEntry` Stack 登録（P1）
5. **M2** — ウイング / チェイス / JC・RC のスコープ ADR

**Tier 3 以降（リファクタと機能を並行）:**

6. Event 層 Phase 1–2（rush / leave / strike のみ）
7. `pendingEffectChoice` kind 別分割
8. 採用キーワードのフレームワーク（JC / RC / ウイング / チェイス）

**Tier 4（プロダクト価値の本体）:**

9. Legend 1–3 effectId 登録 — データ整備 → エンジン → UI の順
